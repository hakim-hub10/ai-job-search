# Authentication Database Foundation

Phase 15.2 uses Better Auth's built-in PostgreSQL/Kysely path with `pg`. Better Auth owns its core authentication schema; the application owns the candidate ownership table.

## Environment

Set these server-only variables before using the auth route:

- `DATABASE_URL`: PostgreSQL connection string.
- `BETTER_AUTH_SECRET`: high-entropy secret with at least 32 characters.
- `BETTER_AUTH_URL`: optional application URL used by Better Auth.

No application startup code runs migrations automatically. Missing configuration fails when an auth/database operation is requested, without printing secrets or connection strings.

## Schema workflow

1. Review the generated Better Auth SQL for the installed package version.
2. Generate a new SQL migration with `bun x auth generate` when the auth schema changes.
3. Add or review the application ownership constraints in the same migration workflow.
4. Apply locally with `bun x auth migrate` only for the built-in Better Auth/Kysely schema, plus the ownership SQL through the normal PostgreSQL migration process.
5. Apply production migrations as an explicit deployment step, never during Next.js startup.

## Migration status

The checked-in `migrations/0001_auth_and_candidate_ownership.sql` is a manually authored, reviewable migration aligned with the installed Better Auth `1.7.3` schema definitions; it is not claimed to have been generated by the Better Auth CLI. In this environment, the current Better Auth CLI generation workflow requires a live PostgreSQL connection. The checked-in migration has not been applied. Local and production migration must be run explicitly by an operator or deployment process, and production backup and recovery should be considered before applying schema changes. Application startup never runs migrations automatically.

The ownership table intentionally stores `candidate_id` as an immutable application identifier without a PostgreSQL foreign key yet because candidates remain in the legacy JSON repository. The `user_id` relationship is constrained against Better Auth's user table.

## Ownership constraints

`candidate_ownership` uses:

- `relationship = 'owner'` as the only Phase 15 MVP value.
- `UNIQUE (user_id, relationship)` to enforce at most one job-seeker owner relationship per user.
- `UNIQUE (candidate_id, relationship)` to prevent two job-seeker owners claiming the same candidate.
- a foreign key from `user_id` to Better Auth's `user.id`.

The one-candidate invariant is completed in the next ownership phase by the server-side account workflow and transaction. This foundation does not migrate existing candidates.

## Runtime boundary

`auth-db.ts`, `auth.ts`, and `auth-session.ts` are server-only. The pool is lazy and process-singleton scoped for Next.js development hot reload. The session helper returns only a minimal user projection and never accepts a client-supplied user ID.

The current `candidateId` routes remain local preview routes and are not authorized by this phase. Authentication foundation does not claim route protection. Candidate ownership enforcement is Phase 15.4-15.6 work.

## Phase 15.3 authentication flow

Email/password registration, login, and logout use Better Auth's official browser client and database-backed sessions. The UI uses fixed internal redirects only; no candidate is created during authentication. Better Auth owns password handling, hashing, session cookies, origin checks, and server-side session invalidation. Email delivery/verification and production-grade login rate limiting are not configured until the later security/UX hardening phases; no fake email sending or custom in-memory brute-force protection is included.
